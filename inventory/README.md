# Inventory

What the Rust rewrite must reproduce, extracted from the C tree. Every `.json` and `.md` here is
generated by `gen/<section>.py`; none is edited by hand. Each records the C commit it describes
(`c-commit`, the last commit outside the rewrite's own paths, `-dirty` if the C tree has local
changes). Paths that belong to the rewrite are listed in `NOT_C_TREE` in `gen/common.py`; add
new top-level rewrite paths there, or every rewrite-only commit makes the inventory look stale.

```sh
python3 inventory/gen/all.py           # regenerate everything
python3 inventory/gen/all.py --check   # also fail if any committed output is stale
```

Run `--check` after the C tree moves; a generator that fails its self-checks writes nothing.

`perf` comes from `inventory/measure/perf.py` the same way (`--run`, about 15 minutes). Its figures
hold for this machine only: compare builds measured here by the same script, never against
numbers from elsewhere.

`baseline` comes from `inventory/measure/baseline.py`, which `all.py` does not run. `--run` configures and builds
the C tree in `build/c`, runs `runtests.pl` and the `tests/http` pytest suite (about seven
minutes; pytest gets a venv in `build/c/pytest-venv`) and parses the results (libraries newer than the distribution's come from
`inventory/measure/deps.py`, under `build/deps`); without
`--run` it only re-parses the stored results, and refuses if they were measured at another C commit.

`inventory/measure/score.py` scores the Rust build the same way: it lays out `build/rust` with the
C build's test servers and programs and the Rust library and tool, checks with `ldd` that the
Rust library is the one loaded, runs both suites and compares each result with `baseline`. Its
results stay in `build/rust/score`. `--lib c` and `--lib stub` arm it (see the script). Tests
replaced by Rust tests (`REPLACED` in `suite.py`, see `SCOPE.md`) are counted apart. Both
scripts run and parse the suites through `inventory/measure/suite.py`.
Lint generators with `scripts/pythonlint.sh inventory/gen/*.py`.

## Sections

| section | what it holds |
|---|---|
| `abi` | Exported functions and prototypes, every public constant with its compiler-computed value and C type, struct sizes and field offsets, typedef sizes, strerror tables, symbol history, soname, version script, pkg-config and curl-config. |
| `options` | CURLOPT, CURLMOPT, CURLSHOPT, CURLINFO, URL API parts and flags, header origins, websocket flags: number, type class, `curl_easy_option_*` row, gcc typecheck class, man page metadata, reserved numbers. |
| `cli` | curl tool options (docs vs `aliases[]` table), `--write-out` variables, exit codes, environment and config-file lookup, generated `src/` files. |
| `features` | Protocol schemes, `curl_version_info` features and the test-gating names derived from them, build options, backends per category, environment variables libcurl reads. |
| `quirks` | Claims from KNOWN_BUGS, TODO, EXPERIMENTAL, DEPRECATE and KNOWN_RISKS. All are hypotheses until a test reproduces them. |
| `tests` | Every `tests/data` case with keywords, features, servers and runner; DISABLED; libtest, unit and tunit programs; the pytest suite; test servers. |
| `baseline` | Measured, not derived: what the C reference build in `build/c` does on the test suite, per test (ok, failed, or skipped with its reason) for both `runtests.pl` and pytest, with the build flags, `curl -V` and the built library's exported symbols. |
| `corpus` | Measured, not derived: real curl command lines (`corpus_lines.json`, from `inventory/measure/corpus_run.py --collect`: every invocation in the shell scripts, Dockerfiles, CI configurations, makefiles and documentation of the distribution's source packages that use the tool or build with it, and of every small golang-, node-, python- and ruby- one, with its package, version, file and line), ranked by `gen/corpus.py` against C's option table: which options, spellings and pairs are used. |
| `corpus_diff` | Measured, not derived: each distinct line of the corpus run by the C tool and the Rust tool with no transfer (`corpus_run.py --diff`), and the differences in exit, output and errors, grouped. |
| `perf` | Measured, not derived: a release build of the reference configuration in `build/c-release`, timed with the `tests/perf` benchmarks and the local parts of `tests/http/scorecard.py`. Medians and interquartile ranges, with the machine it ran on. |

## References

`references/` holds real applications of libcurl, copied unchanged with their licences and
never built: evidence of what applications rely on, to check before choosing to differ from C.
`references/webkit-curl/` is WebKit's curl network backend; its README records the commit it
came from and what it relies on.

## Reading the data

- **Layouts are per target.** `abi.json` records the `target` it was probed on. Struct layouts
  and type sizes hold for that target only.
- **Discrepancies are data.** Where two C sources disagree (docs against the header, the docs
  against the option table), the generator keeps both sides under `discrepancies` and does not
  pick one. Run the C build before deciding which side is right.
- **Doc-derived fields are claims.** Protocol lists, DEFAULT text and anything taken from prose
  describe what the C docs say, not verified behaviour.
- **Some tables are hand-written.** They are anchored to the C sources by checks:
  - the backend library and macro table in `gen/features.py`;
  - the `<server>`-keyword-to-program map in `gen/tests.py`.

  When one of these checks fails, update the table to match the C sources. Do not weaken the
  check.
